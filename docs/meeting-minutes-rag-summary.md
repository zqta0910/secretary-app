# 議事録RAG演習 まとめ

期間: 2026-09-28(計画)〜2026-10-05(完了) / ロードマップ上の位置づけ: フェーズ3「RAG・実務トピック」

## 1. 目的と方針

- 架空のリゾート・レストラン運営の会議議事録(35件)に対して、「先月のクレームの傾向は?」のような質問に、**該当する議事録を根拠にして答える**秘書AIの機能(RAG)を作る
- 方針: **仕組みを学ぶ演習**。誤答が出ることは許容する。議事録を全部AIに渡す方式(全文投入)は、この規模なら正確だが、将来の大規模データを想定して採用しなかった
- 制約: 既存のSupabaseプロジェクトにpgvectorを追加、Claude APIキーはブラウザに出さない、回答には出典(日付・タイトル)を付ける、情報がなければ推測せず「該当なし」と答える

## 2. 作ったもの

```
[データ準備(手動で実行)]
data/meeting-minutes/*.md (35件)
  → npm run ingest (scripts/ingest-meeting-minutes.mjs)
     段落ごとに分割(30文字未満は隣と結合) → 103チャンク
     「タイトル(日付)+本文」をVoyage AIでベクトル化(voyage-4-lite、1024次元)
     service_roleキーでSupabaseに全件入れ替え

[質問への回答(チャットのたび)]
質問 → route.ts → Claude(今日の日付を渡す)が2つのツールから選ぶ
  A. search_meeting_minutes(話題で探す)
     質問をベクトル化 → 候補10件(類似度0.25以上、期間指定可)
     → rerank-3-liteで採点し直し、0.60以上を最大5件
     → ヒットした会議の「全段落」を返す(matched: true/false の印付き)
  B. list_meeting_minutes(期間全体を見る)
     関連度の判定なしで、期間内の会議を新しい順に最大12件返す
  → 日付とタイトルを付けて回答 / 該当なしなら「該当する記録がありません」
```

| ファイル | 役割 |
|---|---|
| `supabase/meeting-minutes-schema.sql` | pgvector、チャンク用テーブル、検索関数。読み取りのみ許可(RLS) |
| `data/meeting-minutes/*.md` | ダミー議事録(3〜9月、5種類の定例会議×7ヶ月) |
| `scripts/ingest-meeting-minutes.mjs` | 取り込み。`--dry-run`で分割結果だけ確認できる |
| `src/lib/voyage.ts` | Voyage AIへの接続(ベクトル化・リランキング) |
| `src/app/api/chat/route.ts` | 7つ目・8つ目のツールと、プロンプト(日付・出典・該当なし・使い分け) |
| `docs/meeting-minutes-rag-eval.md` | 12問の評価記録 |

**キーの使い分け**: 検索はanonキー(読み取りのみ)、データ投入はservice_roleキー(RLSを無視できる強い鍵)。service_roleキーはアプリ本体では使わず、手動実行のスクリプトだけで使う。

## 3. 計画からの主な変更点と理由

| 変更 | 理由(実測で分かったこと) |
|---|---|
| 「80文字未満は結合」→ **30文字** | 日本語は段落が短い(中央値54文字)ため、80だと106段落中101段落が結合され、会議丸ごと1チャンクになった |
| 類似度のしきい値0.5 → **リランキングのスコア0.60で判定** | ベクトル検索の類似度は、このデータでは0.3〜0.7に圧縮され、絶対値で関連の有無を判定できない(関連ありの質問は0.40〜0.67、無い質問も0.28〜0.44)。リランキングなら16個の質問で分離できた(関連あり0.70以上、なし0.52以下) |
| ヒットした会議の**全段落**を返す | 「傾向」の質問で、「指摘」「苦情」と書かれた段落(スコア0.52)が落ち、3件中1件しか答えられなかった |
| **list_meeting_minutes**を追加 | 「先月の議事録をまとめて」は話題がなく、全段落が0.34〜0.43でしきい値に届かず「記録されていない」と誤回答した |
| service_roleキーの導入 | 書き込みを手動スクリプトに限定し、アプリからは読み取りだけにするため |

## 4. 評価結果

- 12問(単発4・期間指定3・集計3・該当なし2)で、**1回目9.5/12(79%)→プロンプト修正後11.5/12(96%)**。詳細は`docs/meeting-minutes-rag-eval.md`
- 1回目の失敗は検索精度ではなく、議事録を追加する前に書いた「どのデータか分からないときは聞き返す」というプロンプトの指示との衝突だった
- 12問では見つからず、**画面で手動確認して初めて**「期間まとめ型」の問題が見つかった

## 5. 技術的な学び

1. **ベクトル検索の類似度は、絶対値で関連の有無を判定できない**。順位は信頼できるが、数値の大きさは使うデータ・モデルで変わる。判定にはリランキング(候補を質問と1件ずつ突き合わせて採点し直す)が有効だった
2. **「仕組みの故障か、数値の性質か」の切り分け方**:保存したベクトルの再現性(同じ文章を再度ベクトル化して1.0000)、SQL関数の計算と手元の計算の一致、順位の妥当性を確認して故障ではないと確定させてから、設計(しきい値)の問題として扱った
3. **機能を足したら、既存のプロンプトの指示との矛盾を見直す**。古い指示が新機能を静かに妨げることがある
4. **AIの回答は「事実」と「検索で見つからなかったこと」を混同しやすい**。「記録されていない」と断定させず、「関連する記録が見つからなかった」と言わせる必要がある
5. **評価の点数より、質問の種類を網羅できているかが重要**。手で触って見つけた問題は質問表に足していく
6. **無料枠の制限**:Voyageは1分に3回程度(1回の検索で2回使う)、Supabaseは1週間ほど無操作だとプロジェクトが一時停止する

## 6. 進め方の学び

- 計画 → フィードバック → 修正版を承認 → 段階ごとに実装・検証、の流れで進めた。調査で裏付けが取れなかった点(Voyageの日本語精度)は、**「不明」と明記して、本実装の前に実測テストする手順を計画に入れた**
- 「しきい値0.40は低すぎないか、基本的なところがずれていないか」という指摘が、根本的な確認(上記2)と、方式の見直し(リランキング)につながった

## 7. 限界・未解決

- 複数の会議をまたぐ経緯の質問(例:提供遅延が最初に出たのは5月)は、最初の記録を拾えず2回とも△。原因は未調査
- **会議の種類での絞り込みがなく、漏れる**:「クレーム対応会議を全期間で一覧にして」と聞くと、実際は7回あるのに5件(4〜8月)しか出ず、3月と9月が漏れた。しかも「全期間で一覧にした」と完全であるかのように回答した
- 評価は各1回(n=1)で、質問も議事録も同じAIが作った。数字は目安であり、一般化できない
- **公開はできない**:テーブルの読み書き制限が緩く、ログイン機能もないため、公開すると誰でもAPI利用料を消費でき、データも書き換えられる

## 8. 実運用に向けた要件メモ(議論の記録)

実際に使う場面を想像して出た要件。

**質問の3つの軸**: ①いつ(日付・期間)②どんな会議(種類・部門。例:レストラン系)③何について(話題。例:ドリンク、料理の味)。たとえば「レストラン系の議事録の中で、ドリンクに関するものをまとめて」は、②で絞ってから③を探す質問。

| 要件 | 内容 | 規模感(私の概算) |
|---|---|---|
| 種類・部門での絞り込み | 会議の種類・部門を項目として持ち、両ツールの絞り込み条件にする | 小(1〜2時間) |
| 網羅性 | 「まとめて」は「漏れなく」の要求。取り込み時にClaudeに各議事録を読ませて部門・話題のタグを付けて保存し、タグで絞る案(タグ付けの精度確認が必要) | 中(半日〜1日) |
| 運用 | 追加・修正・削除、差分取り込み(今は全件作り直しで、件数が増えると時間がかかる)、議事録の整理(分類・アーカイブ) | 中 |
| 選択・追加の画面 | 「この3件だけを対象に質問する」、画面からの議事録の追加。**ログイン・権限が前提** | 大(数日〜) |
| 継続的な評価 | 質問の種類が増えるたびに評価セットを更新し、正答率を測り続ける | 継続 |

**結論**: 個人開発で全部を作るのは大きい。BizDevとしては、顧客が一番困る質問を1〜2個に絞り、上の軸で動く最小版を使ってもらい、残りは「誰が・いつ・いくらで」の提案として整理する進め方が現実的。「データが増えたとき、誰がどう追加し、絞り込み、整理するか」は、顧客が必ず聞く要件であり、要件定義の聞き取り項目として使える。

## 9. 用語(初出のみ)

- **RAG**: 質問に関係する資料を検索で探し、その内容をもとにAIが回答する仕組み
- **embedding(ベクトル化)**: 文章を「意味の近さを表す数値の配列」に変換すること。意味が近い文ほど数値も近くなる
- **チャンク**: 長い文章を検索しやすい単位に分けたもの。今回は段落
- **pgvector**: Supabase(PostgreSQL)にベクトルを保存し、意味が近い順に検索できる拡張機能
- **コサイン類似度**: 2つのベクトルがどれだけ似ているかの指標。ただし今回のように絶対値は当てにならない場合がある
- **リランキング**: 検索で拾った候補を、質問と1件ずつ突き合わせて、本当に答えになっているかを採点し直す機能
- **service_roleキー**: Supabaseの、RLS(読み書きの制限)を無視できる強い権限の秘密鍵。公開してはいけない
