## 1. 概要

- **作ったもの**: メモ・TODO・家計簿・会議議事録の4種類のデータを、チャットで検索・編集(議事録は検索のみ)できる秘書AI。ツールは8個
- **規模**: コミット15回(+この資料)、コード約1,100行(`route.ts` 574行、`ChatApp.tsx` 267行、取り込みスクリプト174行ほか)
- **使った技術**: Next.js / Supabase(+pgvector) / Claude API(Haiku 4.5) / Voyage AI(ベクトル化・リランキング)
- **品質の目安**: 議事録RAGの12問評価で、1回目9.5/12(79%)→修正後11.5/12(96%)。ただし各1回・同じAIが作った質問で、手で触って見つけた問題もある
- **公開はしていない**(理由は7章)。ローカルとGitHub(`zqta0910/secretary-app`)のみ

## 4. 意思決定の記録(あなたの判断が結果を変えた場面)

1. **「しきい値0.40は低すぎないか、基本的なところがずれていないのでは」**(10/3)→ 保存データ・SQL・順位の健全性を確認してから、類似度の数値の性質を突き止め、リランキング導入という方式変更につながった
2. **計画へのフィードバック5点**(9/28)→ 書き込み権限の設計(service_roleキー)、「該当なし」の判定方法、「先月」への対応、日本語対応の裏付け確認が計画に入った。日本語の裏付けは見つからず、「不明」と明記したうえで実測テストを組み込んだ
3. **「RAGを根本から違う方法で試せないか」「今の方式は信憑性に欠けるのでは」**(10/3)→ 全文投入や評価セットという選択肢を比較した。最終的に「大規模データが将来の目標」という理由で現在のRAG続行を判断した
4. **画面で自分で質問して確認**(10/5)→ 12問の評価で見つからなかった「期間まとめ型」の問題を発見できた
5. **番号選択の編集フローを提案**(9/25)→ AIに曖昧な指示を任せず、確定したIDを渡す設計になった

## 5. つまずきと解決

| つまずき | 原因 | 解決 | 学び |
|---|---|---|---|
| `claude`コマンドが見つからない | ターミナル用CLIは別の製品で、未インストール | claude.ai/codeとRemote Controlで同じ会話を見る | デスクトップアプリとCLIは別物 |
| Cursorのサイドバーが別プロジェクトのまま | ファイル単体を開いただけで、プロジェクトは切り替わっていない | 実害なし。仕組みの理解のみ | |
| メモ取得で`fetch failed` | Supabase無料プランが無操作で一時停止(DNSが存在しない状態) | ダッシュボードで再開 | 切り分け: ドメイン全体と案件専用アドレスを比較 |
| 家計簿に31件あるのに「データなし」 | AIがツールを呼ばずに答えた(確率的) | プロンプトで「ツールを使わず断定禁止」 | AIの判断は毎回揺らぐ |
| チャンクが36件しかできない | 日本語は段落が短く、「80文字未満は結合」だと大半が結合された | 30文字に変更 | 英語感覚の基準値は日本語に合わない |
| 全質問が「該当なし」になる | ベクトル検索の類似度が0.3〜0.7に圧縮され、しきい値0.5が高すぎた | リランキングで判定 | 類似度の絶対値は当てにならない |
| Voyageの429エラーが頻発 | 無料枠は1分3回程度の制限 | 待機・再試行、検索中は案内文を返す | 無料枠の制限を設計に入れる |
| 議事録を追加したのに使われない | 古い「どのデータか迷ったら聞き返す」指示との衝突 | 業務質問は先に検索する指示に変更 | 機能追加時は既存の指示との矛盾を見直す |
| 「先月の議事録をまとめて」に「記録されていない」 | 話題がなく関連度の判定で全除外 | 期間で取り出す一覧ツールを追加 | 評価セットは質問の種類を網羅する必要がある |

詳しい技術的な経緯は`docs/meeting-minutes-rag-summary.md`、評価の詳細は`docs/meeting-minutes-rag-eval.md`にあります。

## 6. 進め方の特徴(観察)

**良かった点(根拠つき)**
- **疑問を根本まで確認する**:「0.40は低すぎないか」「根本から違う方法は?」という問いが、方式変更と、評価という視点につながった(4章の1・3)
- **範囲を自分でコントロールする**:「土台作りだけ」「実装前に計画だけ」「ここで一旦完了」と、広げすぎない判断を一貫して行った
- **実際に触って確認する**:評価表では見つからない問題を、自分の手で見つけた(4章の4)
- **記録の習慣**:LOG・用語集・評価記録を、作業の区切りで残している
- **「分からない」を分からないと言う**:日本語対応の裏付けなし、という点を隠さず計画に残せた

**伸ばせる点(提案)**
- **要件を「入力→出力→判断基準」で書く練習**:RAGの要件は、計画へのフィードバックを重ねて具体化した。最初から「どんな質問に、何を根拠に、どうなれば合格か」を書けると、手戻りが減る(議事録RAGの質問表を、実装の前に作る進め方)
- **評価の発想を最初に持つ**:今回は実装後に質問表を作り、見逃しも出た。次は実装前に「質問の種類の一覧」を作る
- **セキュリティを自分の言葉で説明できるか**:anonキーとservice_roleキーの違い、公開できない理由は、顧客に聞かれる内容。説明できるかの確認が必要
- **AIの回答を鵜呑みにしない検証癖**:今回は上手くできている。引き続き、断定的な回答には「根拠は?」と確認する
